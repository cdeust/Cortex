# ADR-1114: The plugin runs its own PostgreSQL from pinned theseus binaries

## Status

accepted (amended 2026-10-17 by the owner's round-4 decisions D1 to D5 on PR #748, and by the round-5 and round-6 reviews)

## Context

Amends ADR-1104 decision 1 (selection order); keeps ADR-1108 (Setup installs, no hook does). Replaces the pg0 design of PR #748 (issue #744), which never merged.

Issue #744 asks for a PostgreSQL the plugin provisions itself, with pgvector and pg_trgm, on a Mac that has no Homebrew (issue #740: the org-managed work Mac). PR #748 embedded pg0 v0.15.2 (vectorize-io/pg0), the latest release (2026-09-14; no later release, its fix pg0#42 unreviewed). Measured 2026-10-17 under `sandbox-exec` with `/opt/homebrew` and `/usr/local` unreadable: pg0's PostgreSQL 18.1.0 loads `/opt/homebrew/opt/openssl@3/lib/libssl.3.dylib` (arm64; `/usr/local/opt/openssl@3` on x86_64) and `pg0 start` dies in dyld; the PR wrote its state before the start, so the failure was permanent. The review of 2026-10-16 also found: hooks ignored `CLAUDE_PLUGIN_OPTION_DATABASE_URL` (two stores), a stale `postmaster.pid` with a reused PID blocked the server (`PermissionError` read as alive), and the password went through argv.

theseus-rs/postgresql-binaries 18.4.0 and later bundle OpenSSL: `otool -L bin/postgres` of 18.6.0 (aarch64 and x86_64 apple-darwin) names only `/usr/lib/libxml2.2.dylib`, `@loader_path/../lib/libssl.3.dylib`, `@loader_path/../lib/libcrypto.3.dylib`, `/usr/lib/libz.1.dylib` and libSystem; 3 of 125 Mach-O files reference a build path, all under `pgxs/src/test`. The trees ship PGXS (`lib/pgxs/src/makefiles/pgxs.mk`, `bin/pg_config`, `include/server`), so extensions can be built against them. The Linux GNU 18.6.0 archives are not self-contained: `postgres` needs the distribution's `libxml2.so.2 libssl.so.3 libcrypto.so.3 libgssapi_krb5.so.2 libzstd.so.1 liblz4.so.1 libz.so.1` and glibc 2.34 (objdump `NEEDED`, version references); musl builds also need ICU 74. The Windows archive bundles its DLLs except `VCRUNTIME140.dll`. theseus commit 78f15cec ("bundle required runtime dependencies", 2026-10-04) is in no release.

The round-3 review (2026-10-17) found three more defects: Setup with a `managed` marker started the managed server although `database_url` was configured (B1); a live PID of this user plus any listener on the recorded port was adopted as the postmaster, and `stop()` ran `pg_ctl stop` on it (B2); `python -m mcp_server.doctor` crashed on a `managed` marker (B3). The owner then decided: Codex and direct launches attach to the managed server (D1); no `pg_ctl -w` timer decides failure, readiness and exit are events (D2); the SQLite fallback is visible (D3); pgvector is compiled by Cortex CI, not taken from a personal repository (D4); the cluster lives next to the global marker so uninstalling a plugin never deletes memories (D5). Measured while implementing D2: `os.pidfd_open` fails with ENOSYS under qemu-user emulation (x86_64 Linux container on an arm64 host), so a per-PID exit event is not portable; an unreaped zombie keeps its `/proc/<pid>/stat` start time.

## Decision

1. **One system, no pg0.** Setup downloads `postgresql-18.6.0-<triple>.tar.gz` (theseus) and `pgvector-<triple>-pg18.tar.gz`, keeps them only when their sha256 equals the pinned digest, lays pgvector's `lib/` and `share/extension/` over the PostgreSQL tree and stamps it last (`scripts/launcher_pg_assets.py`). Pinned triples: aarch64 and x86_64 apple-darwin, aarch64 and x86_64 unknown-linux-gnu. Any other host (native Windows, musl, other CPUs) raises `UnsupportedError` and keeps SQLite.
2. **pgvector is built by Cortex CI (D4).** `.github/workflows/pgvector.yml` (`scripts/pgvector_build.py`) clones pgvector at the pinned upstream tag `v0.8.7`, refuses it unless it resolves to commit `f37c13f6`, builds it with PGXS against the pinned theseus tree on a runner of each triple (`OPTFLAGS=""`, no `-march=native`; on macOS the runner's SDK and the tree's own deployment target), proves it loads (`postgres --single` creates the extension and computes a distance), checks on Linux that no symbol needs more than GLIBC_2.34, packs a deterministic archive, attests its build provenance (`actions/attest-build-provenance`) and publishes the four archives once as a prerelease of this repository, from `refs/heads/main` only (a branch builds and attests, never publishes); an existing release is never modified. The workflow runs when it, the build script or the pins (`launcher_pg_assets.py`) change. The pinned digests are those of the published, attested assets: `gh attestation verify <archive> --repo cdeust/Cortex --source-ref refs/heads/main`. The release `pgvector-v0.8.7-pg18.6.0` was created from the PR branch before this rule; the build is reproducible bit for bit (two runs, same digests), so the main push after the merge attests the same digests from main and prints "release exists: nothing replaced".
3. **The cluster lives next to the marker (D5).** The cluster root is `~/.claude/methodology/managed-pg` (data directory, password file, state JSON, locks, logs); the binaries stay in the Claude Code plugin's data (`<plugin data>/pg/dist`), named by `installed.json`. Uninstalling the plugin removes the binaries, never the memories: the next launch fails with "run `claude --init-only`", and Setup reinstalls the binaries over the kept cluster. `launcher_backend.has_earlier_state` does not count `managed-pg` as earlier Cortex state.
4. **Cortex drives PostgreSQL itself, on events (D2), with a proven identity (B2).** `initdb --pwfile` (the password never reaches argv), `scram-sha-256`, UTF8, C locale, `listen_addresses = '127.0.0.1'`, no unix socket. One detached supervisor per root, ordered by the three `flock` files (clients, start, supervisor), spawns `bin/postgres -D <cluster> -p <port>` as its own child and records `{pid, started, port}`, `started` being the kernel's start time of that PID (`proc_pidinfo` on macOS, `/proc/<pid>/stat` on Linux; none for a zombie). A postmaster is ours only when `postmaster.pid` names this data directory, the recorded PID and port, and the PID is alive as this user with the recorded start time; a reused PID, another user's process (EPERM), a dead PID or a foreign listener is never adopted, dialled or signalled. Only then is the port dialled, and the server must complete SCRAM-SHA-256 with the cluster's password, including the server signature and the nonce (`managed_pg_protocol`; a server that sends a wrong signature, a foreign nonce, AuthenticationOk without the exchange, a cleartext-password request or a malformed server-first message is refused and never receives the password). Whether `postmaster.pid` was written by the live process it names is also a kernel fact: that process started no later than the file's line 3 (`MyStartTime`, whole seconds after exec) plus 2 s (1 s for the whole seconds, 1 s for Linux `btime`; measured kernel start minus a whole-second clock read by the process itself: macOS arm64 max 0.911 s, Linux arm64 max -0.190 s, Linux x86_64 under qemu max -2.520 s). A process that started later is a reused PID and the file is stale. The one other process ever dialled is such a proven writer of a `ready` `postmaster.pid` while a group nothing recorded holds `postmaster.lock` (an exclusive `flock` on a 0600 file in the 0700 root, the boundary that also guards `postmaster.json`): a postmaster whose supervisor died between spawning and recording it. Cortex waits on events until that group exits (then starts its own) or a proven writer reports `ready`; it is adopted and recorded only if it authenticates with the cluster's password, otherwise the start fails naming its PID and port, and it is neither signalled nor its `postmaster.pid` touched. The postmaster inherits the write end of a pipe and an exclusive `flock` on `postmaster.lock`; both pass to every process it forks. Starting waits on kernel events (kqueue on macOS, inotify on Linux) until `postmaster.pid` reports `ready` or the pipe reaches end of file (the group exited: the failure, reported with what it wrote to `postgres.log`); stopping sends SIGINT and blocks on `postmaster.lock`, granted once the postmaster and all its children are gone. An adopted postmaster still starting is stopped and started anew. `postmaster.pid` is removed only while Cortex holds `postmaster.lock` (no postmaster it started is alive) and only when the file is proven stale. A live writer that Cortex did not start (started by hand or by `pg_ctl`; it holds no `postmaster.lock`) is named with its PID and port and left alone: nothing is removed, signalled or dialled, and it is not adopted, because without the lock there is no exit event to supervise or to stop on (the round-5 code removed its `postmaster.pid` and PostgreSQL then shut it down, measured by the round-5 review). When the postmaster dies while clients are attached, its group releasing `postmaster.lock` wakes the supervisor, which, holding the start lock, starts a new one on the same port when that port is free and rewrites `status.json`; a client that reads `running` checks the recorded postmaster with kernel facts and, while it is dead, waits for the next change in the root directory or the supervisor's exit instead of taking a dead URL. A restart that fails records `failed` and the supervisor exits; the next client starts a new supervisor. No `pg_ctl -w`, no sleep, timeout or attempt cap decides anything. A `postmaster.pid` that is not ours is removed before a start, never on stop. The attach code lives in the wheel (`mcp_server/infrastructure/managed_pg*.py`); hooks never install, they only start an installed server (ADR-1108).
5. **Selected only after it proved itself (staged).** Setup's step (`scripts/launcher_pg_provision.py`) installs, initialises, starts, creates the `cortex` database, `vector` and `pg_trgm`, checks pgvector's iterative scan and applies the schema; `setup_db._init_schema` fails on any failed statement. Only then it writes `provisioned.json` and, for an eligible store, the marker `{"backend": "managed", "root": "~/.claude/methodology/managed-pg"}`. A store already managed that fails makes Setup fail.
6. **The fallback is visible (D3).** When an eligible store stays on SQLite because the server cannot run here, Setup records the cause as `sqlite_fallback` in `<key>.setup.json` (kept when a later step fails), prints `SQLite fallback: <cause>`, and the next SessionStart shows the line `SQLite fallback: <cause>` under "Cortex ready" while the store is SQLite.
7. **Selection order, the same on every surface (D1).** (a) A configured database always wins, in launches and in Setup, before any marker is read (B1): `database_url` as `DATABASE_URL`, or for every hook and Setup `CLAUDE_PLUGIN_OPTION_DATABASE_URL` mapped onto it first, or an explicit `CORTEX_*` backend setting; nothing managed is installed or started, and Setup says so. (b) A `managed` marker attaches the process to that root through `backend_marker.apply_backend_resolution` and sets `DATABASE_URL` and `CORTEX_MEMORY_STORE_BACKEND=postgresql`: the Claude Code launcher, `python -m mcp_server` / `hypermnesia-mcp`, the Codex hook entry `mcp_server.hooks.entry` (what `runtime.py` executes) and `cortex-doctor` alike, so Claude and Codex on one HOME share one server and one store. A server that cannot start stops the process with its cause, never a silent switch: the launcher, `python -m mcp_server` and the Codex hook entry print one line `Cortex not ready: <cause>` and exit 1, the doctor reports a failed check (B3). `effective_backend` names `postgresql` for a `managed` marker and starts nothing. (c) Otherwise ADR-1104 unchanged: the marker, or the first-launch decision, SQLite by default.
8. **No migration in this change.** A store is eligible when nothing configures one and none exists: no marker and no earlier Cortex state, or the launcher's own first-launch SQLite marker with no SQLite file at `CORTEX_MEMORY_DB_PATH` / `CORTEX_MEMORY_SQLITE_FALLBACK_PATH` (or their default). An existing SQLite store keeps its marker; a later importer moves it and flips the marker to `managed`.

## Consequences

Positive: on macOS (arm64, and x86_64 under Rosetta) the managed server starts with Homebrew unreadable, `CREATE EXTENSION vector` (0.8.7, built by Cortex CI) and `pg_trgm` succeed, a second process attaching from the marker alone (the Codex hook entry) gets the same server, and it stops when its last client exits (measured 2026-10-17, `scripts/locked_mac_env/managed_pg_e2e.py` under `no_homebrew.sb`, cluster root under `$HOME/.claude/methodology/managed-pg`); the same end-to-end proof passes in an Ubuntu 24.04 arm64 container. The lifecycle tests pass on macOS, Linux arm64 and Linux x86_64 under qemu, in a container without an init process. On Linux GNU it works where the seven libraries are installed (measured round 3: Debian 12 with `libxml2`, Ubuntu 24.04, both CPUs). A failed provision never locks a user out: the next Setup retries while the store is still eligible, and the user is told why SQLite is in use. A slow start (crash recovery, emulation) is waited for as long as the postmaster lives.

Negative, known: a group that holds `postmaster.lock` without being recorded, and that neither exits nor gets a proven writer to report `ready` (a hung `archive_command`, children of a killed postmaster that linger), blocks attach for as long as it lives, with the start lock held: no clock decides that a start failed (D2). Linux distributions without `libxml2.so.2` (measured: Debian 12 slim without it; Ubuntu 25.10, which ships only `libxml2.so.16`) or without OpenSSL 3 or Kerberos' `libgssapi_krb5.so.2` stay on SQLite, with the loader error as the recorded fallback cause, until a theseus release bundles them (78f15cec). Native Windows stays on SQLite: the lifecycle uses POSIX `flock`, and the archive needs the MSVC runtime. A fresh install that skips `claude --init-only` gets the SQLite store at its first launch and keeps it until the importer exists. Setup downloads about 13 MB from GitHub releases once per pinned version; an old tree is not removed when the pin moves. A supervisor killed between spawning the postmaster and recording it leaves a group that holds `postmaster.lock`: the next start adopts it once it proves itself (measured with the fake postmaster; with the real PostgreSQL the round-4 review measured that the earlier code instead deleted the orphan's `postmaster.pid` and recovered only through PostgreSQL's once-a-minute lock-file recheck). Between a postmaster's death and the supervisor taking the start lock, a client that already holds the old URL sees connection errors; it works again once the new postmaster binds the same port, which fails only if another program took that port meanwhile (then that client's URL stays dead until its process restarts). Codex alone (no Claude Code plugin) never gets a `managed` marker, and Codex on a HOME whose Claude Code plugin was uninstalled fails with "run `claude --init-only`" until the binaries are back. A push that changes the pgvector pins on any branch creates the release before review.

Scope of the measurements: macOS arm64 natively and x86_64 under Rosetta on one Mac (macOS 26.6.2); Linux aarch64 natively in containers and Linux x86_64 under qemu emulation on that Mac. The CI job `managed-pg` repeats the proof on macos-latest, ubuntu-latest and ubuntu-24.04-arm, `install-e2e` checks that a fresh install's first session names the PostgreSQL store, and `pgvector` builds and load-tests the archives on macos-15, macos-15-intel, ubuntu-22.04 and ubuntu-22.04-arm. Setup checks eligibility again right before it writes the `managed` marker, so a first launch that chose SQLite while the server was being provisioned keeps its choice.
